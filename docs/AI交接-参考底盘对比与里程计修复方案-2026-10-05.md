## 2. 当前实车现象和已知证据

用户已实测原地旋转约 90°，结果为：

```text
实体车实际转角：约 90°
飞控 IMU 角度变化：约 82°
底盘 /odom yaw 变化：约 19.6°
/odom 同时产生约 0.143 m 假平移
```

这个结果说明：

1. IMU 本次转角测试基本可信，不是只有 20°的真实转动。
2. `/odom` 的转角严重偏小。
3. 原地旋转时理论上左右轮距离一正一负，`(d_left + d_right) / 2` 应接近 0。现在出现 14 cm 假平移，说明左右轮的计数量、方向或两者都有问题。
4. 轮距错误只会按比例放大或缩小 `dtheta`，不能解释原地旋转时的明显假平移。

因此当前不应先调轮距、Cartographer 权重、扫描匹配窗口或 IMU 滤波。先修正底层编码器计数。

## 4. 参考项目一：`ROS_SLAM`

### 4.1 它的整体链路

```text
/cmd_vel
-> chassis_controller.py
-> 字符指令 A-H / I / K / Z 和速度指令
-> 115200 串口
-> STM32 四麦轮速度闭环
-> STM32 回传四轮瞬时速度
-> serial_comm_node.py 发布 wheel_speed
-> odometry_pub_node.py 积分
-> /odom + odom->base_footprint
```

关键文件：

- `example/ROS_SLAM/mc_ws/src/mc_chassis/mc_chassis/chassis_controller.py`
- `example/ROS_SLAM/mc_ws/src/mc_chassis/mc_chassis/serial_comm_node.py`
- `example/ROS_SLAM/mc_ws/src/mc_chassis/mc_chassis/odometry_pub_node.py`
- `example/ROS_SLAM/slam_nv2_ws/src/slam_nav2/params/lds_2d.lua`
- `example/ROS_SLAM/stm32.zip`

### 4.2 它的编码器采集

`stm32.zip` 内的 `stm32/a/HARDWARE/encoder.c` 对 TIM2、TIM3、TIM4、TIM5 都使用：

```c
TIM_EncoderInterfaceConfig(TIMx, TIM_EncoderMode_TI12, ...);
```

即 A/B 两相都进入定时器的硬件 Encoder Mode。固件每 10 ms 读取一次计数器，然后清零，用于轮速闭环。

这个方案比当前项目的“A 相中断 + B 相 GPIO”更直接，方向由 STM32 硬件正交解码确定，不需要在单个通道的中断里复原完整四状态。

### 4.3 它的里程计特点

STM32 发送的是四轮瞬时速度，不是累计计数。ROS2 中的 `odometry_pub_node.py` 再用轮速和到达时间积分。

该项目为了实车效果做了多项经验处理：

- 轮速平移结果整体乘 `2.0`；
- X/Y 又有独立系数 `1.048` 和 `1.063`；
- 检测到转动时，yaw 改用 IMU 角速度积分；
- IMU 角速度轴固定为 `y`，这是它的安装方向，不能照搬；
- `dt` 被限制到 `0.001~0.05 s`；
- 串口轮速帧没有源时间戳、序号和累计计数。

它能建图的关键不是“四轮速度积分一定比累计计数好”，而是底层硬件编码器计数和速度闭环首先可用，并且转动时用 IMU 遮住了一部分轮式 yaw 误差。这个实现可以用来理解“IMU 辅助转弯”，不建议直接复制。

## 5. 参考项目二：`ros2-stm32-autonomous-robot`

### 5.1 它的整体链路

```text
ROS2 /cmd_vel
-> C++ bridge
-> SocketCAN / CAN FD
-> STM32
-> 左右轮独立速度闭环
-> TIM2/TIM3 硬件正交编码器
-> MCU int64 累计轮计数
-> 0x181 WHEEL_STATE（50 Hz）
-> ROS2 bridge 根据累计计数差做差速积分
-> /odom + 唯一 odom->base_link TF
```

关键文件：

- `example/ros2-stm32-autonomous-robot/firmware/App/Src/app_encoder.c`
- `example/ros2-stm32-autonomous-robot/firmware/App/Src/app_drivetrain.c`
- `example/ros2-stm32-autonomous-robot/firmware/App/Inc/app_config.h`
- `example/ros2-stm32-autonomous-robot/interfaces/protocol_v1.md`
- `example/ros2-stm32-autonomous-robot/ros2_ws/robot_stm32_bridge/src/bridge_node.cpp`
- `example/ros2-stm32-autonomous-robot/ros2_ws/robot_slam/config/rplidar_a1_2d.lua`

### 5.2 它的编码器和标定方法

这套方案的关键优点：

1. TIM2/TIM3 使用 `HAL_TIM_Encoder_Start(..., TIM_CHANNEL_ALL)`，A/B 两相由硬件解码。
2. 每次采样都用 `int16_t(current - previous)` 处理 16 位定时器回绕。
3. MCU 保存 `int64_t accumulated_counts`，即使 CAN 丢一帧，下一帧累计值仍然包含完整路程。
4. 编码器 1/2 到左右轮的映射和正转符号独立配置。
5. 左右轮分别手动实测 10 圈，记录为约 1059.5 和 1060.8 count/轮圈，不用规格书猜测。
6. 通信帧有 MCU 单调时间戳、序号、累计计数和有效标志。

### 5.3 它的 ROS 里程计

ROS bridge 中使用标准差速模型：

```text
delta_left  = delta_left_counts  * left_meters_per_count
delta_right = delta_right_counts * right_meters_per_count
delta_center = (delta_left + delta_right) / 2
delta_theta  = (delta_right - delta_left) / track_width
```

它还使用差速圆弧的 SE(2) 增量而不是简单“先转后走”。当前项目在 MCU 中用中点法积分，数学上也是合理的；当前主要问题不在差速公式，而在公式前面的左右轮增量不可信。

### 5.4 它的 SLAM 接法

Cartographer 配置为：

```lua
tracking_frame = "base_link"
published_frame = "odom"
provide_odom_frame = false
use_odometry = true
TRAJECTORY_BUILDER_2D.use_imu_data = false
```

即 bridge 是唯一 `odom -> base_link` 发布者，Cartographer 消费可信的轮式 `/odom`，发布 `map -> odom`。这证明两轮差速车不是必须依靠 IMU 才能建图，但前提是编码器里程计已经通过实车验收。

## 7. 当前项目的底盘链路

```text
ROS2 /cmd_vel
-> ros2_ws/src/wheeltec_chassis/wheeltec_chassis/chassis_bridge.py
-> USART2 115200，0xBB 速度帧，20 Hz 持续发送

-> 编码器增量做差速积分
-> STM32 回传 0xCC x/y/theta 绝对位姿，50 Hz
-> chassis_bridge.py
-> /odom + odom->base_link
```

关键文件：

- `Telemetry framework/Device/Hardware/encoder.c`
- `Telemetry framework/Device/Hardware/encoder.h`
- `Telemetry framework/Appliaction/Chassis_task.c`
- `Telemetry framework/Appliaction/Chassis_protocol.c`
- `ros2_ws/src/wheeltec_chassis/wheeltec_chassis/chassis_bridge.py`
- `ros2_ws/src/lslidar_driver/config/lsn10.lua`

当前协议的优点：

- MCU 发送累计 x/y/theta，不是单帧速度，丢一帧不会直接丢掉全部路程；
- 115200 的数据量足够，底盘 `/odom` 大幅错误不是 WiFi 带宽造成的；
- Jetson 端统一发布 `/odom` 和 `odom -> base_link`。

当前不足：

- Jetson 只收到已积分的 x/y/theta，看不到左右轮原始计数；
- 0xCC 帧没有源时间戳、序号、左右轮累计值和有效状态；
- ROS 消息的时间戳是 Jetson 收包时刻，不是 MCU 采样时刻；
- 编码器输入恢复时使用 `GPIO_NOPULL`，需根据实际编码器输出类型确认是否需要上拉；
- 现有诊断函数会干扰正常计数，见第 9 节。

## 8. 根因：当前编码器解码方式不匹配

### 8.1 硬件和中断方式

当前 PCB 的编码器 A 相接在定时器 CH3，无法直接使用 STM32 只支持 TI1/TI2 的标准 Encoder Mode。当前固件采用：

- 左轮 A：PE13 / TIM1_CH3，双边沿输入捕获；
- 左轮 B：PE11，普通 GPIO 输入；
- 右轮 A：PA2 / TIM2_CH3，双边沿输入捕获；
- 右轮 B：PA3，普通 GPIO 输入。

所以固件只在 **A 相上升沿和下降沿**进入中断，B 相变化不会进入编码器中断。这是合法的 2 倍频软件解码方案，但必须使用“A 边沿时刻的 A/B 电平关系”判方向。

### 8.2 当前代码为什么错

`Telemetry framework/Device/Hardware/encoder.c` 的 `Encoder_CaptureIRQ()` 现在使用完整 AB 四状态机：

```text
00 -> 01 -> 11 -> 10 -> 00
```

这种状态机要求 A 或 B 每次变化都被采样。但当前只在 A 相边沿中断。以注释定义的正转时序为例：

```text
真实状态：00 -> 01(A变) -> 11(B变) -> 10(A变) -> 00(B变)
程序看到：00 -> 01             -> 10
```

`01 -> 10` 是两个 bit 同时变化的跨状态跳转。当前 `switch(prev)` 会将它当作反向，因此同一个真实方向的连续 A 边沿可能一次 `+1`、一次 `-1`，产生大量抵消和错误符号。

这与“实车转 90°，odom 只转约 20°，并且产生假平移”高度一致。

### 8.3 正确的 2 倍频判向

当只在 A 相双边沿进入中断时，每次读当前 A 和 B：

```text
A != B -> 一个方向
A == B -> 反方向
```

当前文件头部已把 `A != B` 定义为原始正转。实际车轮前进符号仍由 `Encoder_SetDirSign()` 的左右轮独立符号修正。

建议的 ISR 核心形式：

```c
a_level = ...;
b_level = ...;

if (a_level != b_level) {
    s_raw_count[id]++;
} else {
    s_raw_count[id]--;
}
```

修改后不再需要 `s_last_state`、`prev`、`code`、`diff`和四状态 `switch`。不要在这一步同时改轮距、每圈计数或 Cartographer 参数。

## 9. 编码器修复必须同时处理的诊断问题

### 9.1 `Encoder_TakeIsrCount()` 会破坏正常里程计

当前它读取后直接将 `s_raw_count[id] = 0`。但 `s_raw_count` 同时是 `Encoder_Update()` 计算里程的正常数据源。调用诊断函数会让 `s_last_raw` 与 `s_raw_count` 失配，下一次更新生成虚假大增量。

建议：

- 新增独立的 `volatile uint32_t s_isr_edge_count[ENC_COUNT]`；
- 每次有效 CC3 中断只对该计数器 `++`；
- `Encoder_TakeIsrCount()` 只读取并清零 `s_isr_edge_count`；
- 不能再写 `s_raw_count`；
- 返回类型可保持现有 API，但内部最好使用无符号边沿计数。

### 9.2 `Encoder_SelfTest()` 不能继续用净方向计数验证边沿数

现有自检固定 B 相，只软件交替翻转 A 相。在正确的 `A != B / A == B` 判向下，A 上升和下降会被判成相反方向，净 `s_raw_count` 本来就可能接近 0。所以不能再用净计数判断中断通路是否工作。

建议修改自检：

1. 自检前记录独立 `s_isr_edge_count` 的值。
2. 软件翻转 A 相。
3. 用“捕获到的边沿总数”判断捕获/NVIC/ISR 链路，不用有符号净位移。
4. 自检后恢复定时器复用输入时，重新确认当前 A/B 电平，避免制造一次虚假边沿。

### 9.3 GPIO 上拉必须根据电气类型处理

现有输入恢复使用 `GPIO_NOPULL`。`ROS_SLAM` 和成熟差速参考都对编码器输入使用了上拉基线，但不能不看硬件直接照搬。

下一个 AI 需要先确认：

- 编码器输出是推挽还是开漏/开集；
- PCB 是否已经有外部上拉；
- 静止时 A/B 是否有悬空或边沿噪声。

只有确认需要内部上拉后，才将 A/B 相相关初始化统一改为 `GPIO_PULLUP`。这一项不是本次已证实的主根因。

## 10. 建议修改计划

### 阶段 A：只修编码器采集和诊断

修改文件：

- `Telemetry framework/Device/Hardware/encoder.c`
- `Telemetry framework/Device/Hardware/encoder.h`
- 如果自检显示语义变化，同步检查 `Telemetry framework/Appliaction/Chassis_task.c/.h`

必做修改：

1. `Encoder_CaptureIRQ()` 改为 A 相边沿时用 `A != B` 判一个方向，`A == B` 判反方向。
2. 删除或停用不匹配当前采样方式的四状态跳转判断。
3. 新增独立 ISR 边沿计数，修复 `Encoder_TakeIsrCount()` 不得破坏 `s_raw_count`。
4. 修改 `Encoder_SelfTest()` 和注释，自检验证边沿总数，不验证固定 B 时的有符号净计数。
5. 核对文件头、`encoder.h`、OLED 诊断文字与新语义一致。

阶段 A **不要改**：

- `WHEEL_SEPARATION_M`；
- `ENC_LEFT_DISTANCE_SCALE` / `ENC_RIGHT_DISTANCE_SCALE`；
- `/scan` 角度方向；
- IMU 轴和符号；
- Cartographer 权重和扫描匹配参数；
- 串口协议格式。

### 阶段 B：烧录后先验证原始轮计数

不启动 SLAM，先把车架起，分别测试。

| 测试 | 必须看到的结果 |
|---|---|
| 左轮单独向前 | 左轮计数稳定单调，归一化后为正 |
| 左轮单独向后 | 左轮计数稳定反向，归一化后为负 |
| 右轮单独向前 | 右轮计数稳定单调，归一化后为正 |
| 右轮单独向后 | 右轮计数稳定反向，归一化后为负 |
| 静止 30 s | 计数不持续增长，边沿诊断接近 0 |
| 同一轮连续同向转 | 不得出现明显的 `+1/-1` 交替抵消 |

如果只是整轮符号反了，只调该轮 `CHASSIS_ENC_LEFT_SIGN` 或 `CHASSIS_ENC_RIGHT_SIGN`，不要改 ISR 判向真值表来对不同轮做特例。

### 阶段 C：实测每轮一圈计数和距离比例

1. 每个物理车轮独立向前转 10 整圈。
2. 记录左右轮累计计数，分别除以 10。
3. 不要只用 `13 线 * 30 减速比 * 2 倍频 = 780`宣称标定完成，理论值只用于判断数量级。
4. 再用地面直行 1~2 m 标定左右轮有效 `meters_per_count`。
5. 左右轮可保留独立的 `ENC_LEFT_DISTANCE_SCALE` 和 `ENC_RIGHT_DISTANCE_SCALE`。

这一阶段通过前，不调轮距。

### 阶段 D：验证差速 `/odom`

先不启动 Cartographer，通过 `/cmd_vel` 和 `/odom` 做三类测试：

1. **直线**：实车前进 1 m，`odom x/y` 的距离误差和横向偏移可量化。
2. **原地左转/右转**：左右轮增量必须一正一负，`ds` 接近 0，odom 平移应很小。
3. **90°、180°、360° 旋转**：计算实际 yaw 比例，这时才标定 `WHEEL_SEPARATION_M`。

只有左右轮计数、直线距离和原地旋转假平移都通过后，才认为 `/odom` 可接入 SLAM。

### 阶段 E：改善上位机可观测性（建议，不是第一步）

现有 0xCC 只发 x/y/theta，调试底盘时证据不足。编码器基本修复通过后，可考虑协议升级，增加：

- MCU 单调时间戳；
- 帧序号；
- 左右轮 `int32/int64` 累计计数；
- 左右轮速度；
- 编码器数据有效位和异常计数。

两种可选架构：

1. **保持 MCU 积分 x/y/theta**，另外发诊断帧。改动小，适合当前项目。
2. **MCU 发累计左右轮计数，ROS bridge 积分 `/odom`**。更接近成熟参考项目，可观测性和可标定性更好，但协议和 Jetson 代码改动更大。

不论选哪种，都应保证只有一个 `/odom` 和 `odom -> base_link` 发布权威。

### 阶段 F：最后再把 odom 接回 Cartographer

当前 `ros2_ws/src/lslidar_driver/config/lsn10.lua` 为保护建图，使用：

```lua
tracking_frame = "imu_link"
published_frame = "base_link"
provide_odom_frame = true
use_odometry = false
TRAJECTORY_BUILDER_2D.use_imu_data = true
```

这是底盘 `/odom` 不可信时的临时方案，不是最终底盘里程计方案。

在阶段 B~D 通过后，再分一次单独修改尝试：

```lua
published_frame = "odom"
provide_odom_frame = false
use_odometry = true
```

`tracking_frame` 和 `use_imu_data` 先保持现状，不要在同一次测试中同时关闭 IMU。这样能单独判断“修好的 odom”是否减少转弯重影。

如果 `/odom` 通过了底盘验收，但加回 Cartographer 后仍有转弯重影，再分别检查：

- `/scan`、`/imu/data`、`/odom` 源时间和到达时间；
- `base_link -> laser` 和 `base_link/imu_link` 静态 TF；
- IMU yaw 轴、符号、单位和协方差；
- 激光一圈扫描时间和运动畸变；
- Cartographer 日志中的数据队列和 TF 超时。

这些是第二层问题，不能用它们跳过已证实错误的编码器里程计。

## 11. 关于“转弯直接用 IMU”的决策

可以用 IMU 帮助 yaw，但不建议现在用 IMU 直接遮盖错误轮计数，原因是：

- 原地转弯的假平移由 `(d_left + d_right)/2` 生成，只替换 yaw 不会自动消除假平移；
- 轮计数还用于轮速闭环和直线控制，不能只在 ROS 端绕开；
- IMU 角速度积分有零偏和长时间漂移，应作为融合观测，不是错误编码器的永久替代。

后续如果需要融合，建议在轮式里程计验收后再评估 `robot_localization` EKF，输入轮式平移/速度和 IMU yaw rate。不要第一步就增加融合层。

## 13. 完成标准

底盘阶段完成必须同时满足：

- 左右轮单独正反转计数均能稳定变号；
- 每轮多圈计数重复性可接受；
- 原地左右转时左右轮计数一正一负；
- 原地约 90°旋转时 `/odom` 假平移从当前约 14 cm 明显降低；
- 直线距离误差先通过左右 `meters_per_count` 标定；
- 旋转角度比例再通过有效轮距标定；
- 启用 `use_odometry=true` 后，转弯重影和地图飘移相比当前有明显改善；
- `/odom`、TF 和 Cartographer 没有重复发布权威。

## 14. 最终结论

其他项目与当前项目最关键的差别，不是使用了不同 SLAM 算法，而是它们在 SLAM 之前已经建立了可信的轮计数链路。

当前项目的差速里程计公式本身是标准的，串口带宽也足够。当前最可疑且能解释实测现象的根因是：

> 当前只在 A 相双边沿中断，却使用了要求 A/B 所有边沿都被采样的四状态机，造成轮计数方向误判和大量抵消。

合理的修复顺序是：

```text
修正 A 相双边沿判向
-> 隔离诊断计数与正常里程计
-> 验证左右轮正反转符号
-> 实测每轮多圈计数
-> 标定左右距离比例
-> 验证原地旋转假平移
-> 最后标定有效轮距
-> 打开 Cartographer use_odometry
-> 单独验证转弯重影
```

不应继续用 Cartographer 参数、IMU 积分或缩小车速来遮盖底层轮计数错误。
