### 冲突检查结论

- PA2 / PA3 / PE11 / PE13 在 `.ioc` 中原本**均未占用**，无冲突。
- TIM1 / TIM2 原本**完全没被使用**（工程只用了 TIM3 PWM、TIM4 舵机、TIM6 100Hz 时基），时钟和中断都空着。
- UART4 仍然在 PA0/PA1，不受影响。
- `EXTI15_10_IRQHandler` 已被按键（PC13）占用，但编码器走定时器捕获中断，**不抢 EXTI**。

### 为什么不配 CubeMX 的 Encoder Mode

STM32 的硬件正交编码器模式（`SMS = 001/010/011`）**只能把 TI1/TI2 映射到 CH1/CH2**。本板编码器固定在 CH3 上，CubeMX 的 Encoder Mode 根本不接受这些引脚。

因此采用等效方案：

- **A 相所在的 CH3** 配成双边沿输入捕获 → 每个边沿进一次中断 → 2 倍频计数
- **B 相所在的 CH2/CH4** 配成普通数字输入 → 在中断里读它的电平判方向

判据（A 相跳变那一刻）：`A != B` → 正转；`A == B` → 反转。

代价是分辨率减半（2 倍频而非 4 倍频），但一根线都不用动。

### 备用资源

PA2/PA3 **同时是 TIM5_CH3/TIM5_CH4**，而 TIM5 是 32 位且当前完全空闲。如果以后发现两轮中断太挤，右轮可以整体换到 TIM5，等于天生预留了一条独立通道。

## 四、CubeMX 该怎么处理

### 结论：编码器这 4 个脚，CubeMX 里什么都不用配

代码本身已经能跑，**不需要在 CubeMX 里新勾任何外设**。原因是：

1. 编码器不能用 Encoder Mode（见上），勾了反而配不出 CH3/CH4 捕获；
2. TIM1/TIM2 的输入捕获配置已经按 CubeMX 风格写进 `Core/Src/tim.c`，
   GPIO 复用/普通输入写在 `HAL_TIM_IC_MspInit()`，NVIC 中断在 `encoder.c` 里使能。

**不要**去 CubeMX 里把 TIM1/TIM2 的 `Combined Channels` 选成 `Encoder Mode` —— CubeMX 会拒绝这 4 个引脚（PE11/PE13/PA2/PA3），而且会把 `tim.c` 里的捕获配置冲掉。

### 如果你希望 .ioc 里能看到这 4 个脚（可选，只为可读性）

在 `Telemetry framework.ioc` 里给 4 个脚补上普通输入声明，这样 CubeMX 打开时能看到引脚被占用，不会误分配给别人：

```ini
PA2.GPIOParameters=GPIO_PuPd,GPIO_Label
PA2.GPIO_Label=ENC_R_A
PA2.GPIO_PuPd=GPIO_NOPULL
PA2.Locked=true
PA2.Signal=GPIO_Input

PA3.GPIOParameters=GPIO_PuPd,GPIO_Label
PA3.GPIO_Label=ENC_R_B
PA3.GPIO_PuPd=GPIO_NOPULL
PA3.Locked=true
PA3.Signal=GPIO_Input

PE11.GPIOParameters=GPIO_PuPd,GPIO_Label
PE11.GPIO_Label=ENC_L_B
PE11.GPIO_PuPd=GPIO_NOPULL
PE11.Locked=true
PE11.Signal=GPIO_Input

PE13.GPIOParameters=GPIO_PuPd,GPIO_Label
PE13.GPIO_Label=ENC_L_A
PE13.GPIO_PuPd=GPIO_NOPULL
PE13.Locked=true
PE13.Signal=GPIO_Input
```

这样配置是安全的：`MX_GPIO_Init()` 先把 4 个脚初始化成普通输入，
随后 `MX_TIM1_Init()` / `MX_TIM2_Init()` 里的 MspInit 再把它们改成复用功能，顺序上不会打架。
（**改 .ioc 前先备份**，改坏了自己能退回去。）

## 四之二、踩过的坑：L6218E Undefined symbol Encoder_CaptureIRQ

**现象**：`encoder.c` 编译通过，链接时报
`Error: L6218E: Undefined symbol Encoder_CaptureIRQ (referred from stm32f4xx_it.o)`。

**原因**：本工程 Keil AC5 下 `.c` 文件实际是按 **C++** 编译的
（实测 `encoder.o` 里 `Load`、`TB6612_Init`、`Chassis_Init` 全是 C++ 修饰名）。
于是：

- `encoder.c` 里定义出的符号是 C++ 修饰名 `_Z18Encoder_CaptureIRQP11TIM_TypeDef`
- 而 `stm32f4xx_it.o` 里要的是 C 名字 `Encoder_CaptureIRQ`

名字对不上，就找不到定义。

**修复**：给 `encoder.h` 和 `Chassis_task.h` 加上 `extern "C"` 包裹（已做）。

**同一原因导致的一个更隐蔽的坑**：`TIM1_CC_IRQHandler` / `TIM2_IRQHandler`
在没有原型声明时也是 C++ 修饰名，**覆盖不了 startup 文件里的 `[WEAK]` 弱符号**。
后果是链接照样通过，但中断跑进了 startup 的默认死循环 `B .`，
表现为"烧写后轮子怎么转计数都不动"，而且**没有任何编译/链接报错**。
修复方式是把这 4 个原型放进 `stm32f4xx_it.h` 的 `extern "C"` 块里（已做）。

## 五、标定与验证步骤（按顺序做，每步都要过）

### 第 1 步：确认中断在跑

1. 烧写后，手转右轮，OLED 第 1 行 `EL,ER` 里 ER 应该变化。
2. 手转左轮，EL 应该变化。
3. 若某个轮子**完全不动**：检查 `PA2/PE13` 焊接、编码器供电、以及 `HAL_TIM_IC_Start_IT` 是否被调用。

### 第 2 步：确认方向

1. 用手把右轮**往前**转，看第 1 行 `cL,cR` 是增大还是减小。
2. 若减小，把 `Chassis_task.c` 里的 `CHASSIS_ENC_RIGHT_SIGN` 改成 `-1`。
3. 左轮同理改 `CHASSIS_ENC_LEFT_SIGN`。
4. **不要改线**，符号在软件里改。

> **实测结果（2026-10-01）**：往前推左轮 EL **减少**，右轮同样减少。
> 已把 `CHASSIS_ENC_LEFT_SIGN` 和 `CHASSIS_ENC_RIGHT_SIGN` 都设为 `-1`。✅

### 第 3 步：标定每米计数

1. 手推车沿尺子走一段（越长越准，**至少 1 m**），读第 3 行 `d(mm)`。
2. 理论值应为 `3820 count/m`（`ENC_COUNTS_PER_REV` 780 ÷ 周长 0.2042 m）。
3. 换算系数：`修正系数 = 3820 / 实测count每米`
4. 明显偏离时改 `encoder.h`：
   - 改 `ENC_LINES_PER_REV`：新值 = 旧值 ÷ 修正系数
   - 或改 `ENC_GEAR_RATIO`：新值 = 旧值 × 修正系数（推荐，通常减速比标称更不准）

> **实测结果（2026-10-01）**：推 20 cm（±1 cm）得到右轮 −794、左轮 −770 计数，
> 折合 3970 / 3850 count/m，平均 3910 count/m，与理论 3820 相差 +2.4%。
> **结论：可以接受，暂不修正。** 偏差主要来自 20 cm 这个短距离的读数误差
> （±1 cm 就是 ±5%），另外轮胎实际滚动的有效半径也不等于 32.5 mm。
> 要判断是否需要修正，请推到 **2 m 以上** 再算一次；若偏差仍稳定超过 ±5%，
> 再按上面的公式调 `ENC_GEAR_RATIO`（3910/3820 → 30 × 1.0235 ≈ 30.7）。

#### 排查：计数疯涨（2026-10-01 遇到的第二个问题）

**现象**：推 20 cm，`cL` 显示 `−195075`，`d(mm)` 显示 `−5107`，
但同一时刻里程计 `x` 只有 `0.192`。

**换算一下就露馅了**：
```
195075 count ÷ 3910 count/m = 49.9 m     ← 电机全速转半分钟才有这么多
0.192 m × 3910 count/m = 751 count       ← 这才是真实位移
```
两个数字差了 260 倍。**说明真实位移是准的，多出来的计数是空闲时灌进去的噪声。**

**最可能的原因**：编码器输出是**集电极开路(OC)或开漏**，而输入引脚配了 `GPIO_NOPULL`。
引脚悬空时电平漂在 1.6 V 附近来回抖，输入捕获把它当成连续边沿，
每毫秒能造出几百次假中断。

**已做的修复**（都在 `tim.c` 的 `HAL_TIM_IC_MspInit` / `MX_TIM1_Init` / `MX_TIM2_Init`）：

| 修改 | 原值 | 新值 | 作用 |
|---|---|---|---|
| A 相 GPIO `Pull` | `GPIO_NOPULL` | `GPIO_PULLUP` | 把空闲电平钉在 3.3 V |
| B 相 GPIO `Pull` | `GPIO_NOPULL` | `GPIO_PULLUP` | 同上（判方向也不会乱） |
| 捕获 `ICFilter` | `4` | `8` | 采样窗口 ~0.19 µs → 3 µs，滤掉毛刺 |

> 内部上拉约 40 kΩ。即使编码器是推挽输出，上拉也只会多耗 0.08 mA，
> 不会影响电平判定。如果板上已经有外部上拉，两者并联只是更强，同样安全。

**如果修复后计数仍然疯涨**，请先把**电机电源断掉、轮子完全静止**，
看诊断视图（见下）的 `ISR L/R` 是否为 0。

### 诊断视图：直接看引脚上的边沿频率

主循环每 2 秒在两种显示之间切换。**诊断视图**长这样：

```
ISR L: 0            ← 左轮捕获中断频率 (Hz)
ISR R: 0            ← 右轮
cL,cR: 0,0          ← 累计计数
x,th : 0.000,0.000
```

判读方法：

| 观察 | 结论 |
|---|---|
| 轮子静止、电机断电 → `ISR` 稳定为 **0** | ✅ 信号干净，之前的噪声已解决 |
| 轮子静止 → `ISR` 几十~几百 kHz | ❌ 引脚仍有干扰 / 编码器输出确实悬空 |
| 手匀速转轮子 → `ISR` 正比于转速 | ✅ 解码正常 |
| 全速转 → `ISR` 约 5 kHz | ✅ 与理论一致 |

**理论对照表**（13 线、2 倍频 = 每电机轴 1 圈 26 次中断）：

| 电机轴转速 | 预期 ISR |
|---|---|
| 1 转/秒 | 26 Hz |
| 10 转/秒 | 260 Hz |
| 100 转/秒 | 2.6 kHz |
| 200 转/秒（全速） | 5.2 kHz |

> 轮子转速 = 电机轴转速 ÷ 30。所以 200 转/秒的电机轴对应轮子约 6.7 转/秒，
> 按 0.065 m 轮径算就是约 1.36 m/s——已经超过我们 0.6 m/s 的限速了。

### 第 4 步：标定轮距

⚠️ **前提：车必须放在地面上走，不能架空转轮子。**

1. 在地面画一条起始线，把车放上去，轮胎触地点对准线。
2. 前推 5 cm 让轮胎压实、消掉传动间隙，然后**清零里程计**（按 USERKEY，或调 `Chassis_ResetOdom()`）。
3. 抓住车体，绕**两轮中心连线的中点**原地转**正好 1 圈（360°）**，
   用地面记号或胶带辅助，误差控制在 ±10° 内。
4. 读第 4 行 `th`，理论值 `+6.283` rad。
   - 车**逆时针**（车头往左）转 → `th` 应为**正**
   - 车**顺时针**转 → 应为 `-6.283`
5. 修正公式：`新轮距 = 旧轮距 × (实测 theta / 理论 theta)`

> **踩过的坑**：第一次测试是"把轮子转了一圈"读到的 `th ≈ -0.3`，这个数**不能用**。
> 原因：轮子架空时两个轮子的净位移为零，`dtheta = (dR − dL) / 轮距` 里
> 剩下的只有**两个计数之间的噪声差**（每圈几个计数），
> 除以 0.158 后被放大成零点几弧度——**是纯噪声，不是标定值**。
> 必须让车真的在地上打转，两轮走出的弧长才会产生 `±0.496 m` 的净差。

### 第 5 步：速度环

1. 把 `Chassis_task.c` 的 `s_speed_loop_en` 初始值改成 `1`，或调 `Chassis_SetWheelSpeed(0.2f, 0.2f)`。
2. 先把 `Ki` 设为 0，只调 `Kp`（初始 60），加到"能跟住速度但轮子不发抖"。
3. 再加 `Ki`（初始 12），消掉稳态误差。
4. 观察第 2 行 `v(mm/s)` 是否稳定跟住目标值。
