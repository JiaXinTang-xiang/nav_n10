## 1. 用户当前目标

用户要完成以下闭环：

1. Jetson 运行雷达、飞控 IMU、底盘桥接、Cartographer 和 Nav2。
2. PC 只运行 RViz，通过 CycloneDDS 查看 Jetson 数据。
3. Cartographer 建图后保存 `pbstream` 和 `pgm/yaml`。
4. 重新加载 Cartographer 地图进行纯定位导航。
5. 底盘最高直线速度暂定 `0.15 m/s`。
6. 原地转弯速度范围为 `0.4～0.65 rad/s`；由于底盘低于约 `0.60 rad/s` 可能无法起转，当前参数使用 `0.60～0.80 rad/s`。
7. 转弯使用飞控 IMU 角度闭环；不要把终点方向自动旋转默认塞入普通导航行为树。
8. 重点解决转弯重影、导航原地转圈和偶发约 `1.8 s` 的数据/TF 延迟。

## 2. 当前系统架构

```text
PC
└── RViz2 + CycloneDDS
    └── 只观察 /map /scan /odom /tf，并发送 RViz 初始位姿和导航目标

Jetson
├── lslidar_driver_node      -> /scan
├── anoros_dt                -> /imu/data
├── chassis_bridge           -> /odom、odom -> base_link、接收 /cmd_vel
├── robot_state_publisher    -> base_link -> laser、base_link -> imu_link
├── Cartographer             -> map -> odom
└── Nav2                     -> /cmd_vel_nav -> velocity_smoother -> /cmd_vel
```

### TF 唯一所有权

必须始终保持：

```text
Cartographer:          map -> odom
chassis_bridge:        odom -> base_link
robot_state_publisher: base_link -> laser
robot_state_publisher: base_link -> imu_link
```

禁止同时运行 AMCL 和 Cartographer。禁止启动两个 Cartographer。否则会出现地图跳动、转圈、TF 时间错误和 RViz 队列堆积。

## 3. 当前已完成的修改

### 3.1 Cartographer 配置

文件：`ros2_ws/src/lslidar_driver/config/lsn10.lua`

当前核心配置：

```lua
tracking_frame = "base_link"
published_frame = "odom"
odom_frame = "odom"
provide_odom_frame = false
publish_frame_projected_to_2d = true
use_pose_extrapolator = true
use_odometry = true
TRAJECTORY_BUILDER_2D.use_imu_data = false
```

原因：

- `odom -> base_link` 已由底盘桥接发布，Cartographer 只负责 `map -> odom`。
- 角度已经在 `chassis_bridge` 中用飞控 IMU 修正，Cartographer 不再重复直接使用同一 IMU 作为 2D 姿态输入。
- `use_pose_extrapolator = true` 与参考的差速车工程一致，用最近的 `/odom` 将扫描时刻的位姿外推到当前查询时刻，减少导航查询到旧 `map -> odom` 的概率。

### 3.2 底盘桥接

文件：`ros2_ws/src/wheeltec_chassis/wheeltec_chassis/chassis_bridge.py`

当前逻辑：

- 解析 `0xCC` 或 `0xCD` 底盘遥测帧。
- `0xCD` 使用 MCU 单调 tick 计算左右轮累计计数差。
- 使用独立的左右轮 `meters_per_count`。
- 使用 `wheel_separation = 0.1431 m`。
- 用左右轮平均距离积分 `x/y`。
- 用左右轮差速角计算平移增量。
- IMU 数据新鲜时，用飞控 IMU 的连续 yaw 替换该次 `dtheta`。
- `/odom` 和 `odom -> base_link TF` 使用同一次 ROS `now` 时间戳。
- `/cmd_vel` 超时后发送停车指令。

当前配置文件：`ros2_ws/src/wheeltec_chassis/config/chassis.yaml`

重要参数：

```yaml
left_meters_per_count: 0.0002613638
right_meters_per_count: 0.0002611298
wheel_separation: 0.1431
use_imu_yaw: true
imu_force_gyro_yaw: true
```

底盘编码器和固件的验收记录见 `docs/底盘里程计重新验收-2026-10-06.md`。不要在没有新实测证据时继续修改编码器参数。

### 3.3 Nav2 行为树和 IMU 转弯

已完成：

- `wheeltec_nav2/CMakeLists.txt` 增加 Nav2 BT 插件导出。
- `nav2_params.yaml` 增加 `RemovePassedGoals` 等插件。
- `navigate_to_pose_safe.xml` 删除默认终点 `FinalImuSpin`。
- `navigate_to_pose_with_imu_heading.xml` 保留独立测试用的 IMU 终点旋转。
- `imu_spin_controller.py` 验证过 90°、180°目标，误差约 2°。
- `behavior_server` 的 `spin` 插件替换为 `wheeltec_nav2/ImuSpin`。
- `wait_for_localization.py` 要求 `map -> base_link` 连续新鲜后才启动 Nav2。

删除默认 `FinalImuSpin` 的原因：

RViz 的导航目标包含方向四元数。旧行为树会把目标方向当作必须完成的终点旋转，曾经触发约 `-97°` 的 IMU 旋转。用户看到的“到目标后又转圈”有一部分就是这个行为，不是底盘失控。

注意：删除 BT 的终点旋转不能保证 DWB 永远不旋转。DWB 的 `RotateToGoal`、`GoalAlign`、`PathAlign` 仍可能在跟随路径过程中输出角速度。若用户仍看到持续原地转圈，应检查 `/cmd_vel_nav`、`/cmd_vel` 和 Nav2 日志，不能只看 IMU 插件。

## 6. 当前实际测试结果

### 6.1 Jetson 端实时数据

2026-10-07 在 Jetson 上测得：

```text
/scan     约 10 Hz，topic delay 约 0.100～0.137 s
/odom     约 50 Hz，topic delay 约 0.001～0.003 s
/imu/data 约 100 Hz，topic delay 约 0.001～0.004 s
```

Cartographer 日志显示：

```text
odom rate: 50.00 Hz
scan rate: 10.02 Hz
pulsed at 约 100% real time
```

这说明在该次采样窗口中，Jetson 没有持续 1.8 秒积压。

### 6.2 Jetson 端 TF 年龄

同一次采样中：

```text
map -> odom       约 0.032～0.050 s
odom -> base_link 约 0.016～0.018 s
map -> base_link 约 0.032～0.050 s
```

因此当前运行时刻的 TF 链是新鲜的。之前出现的约 `1.8 s` 错误仍需按“偶发积压/进程卡顿/旧节点并存”继续抓取，不能用一次稳定采样宣布问题已经根治。

### 6.3 PC 端 `ros2 topic delay` 的误区

PC 上曾出现：

```text
/scan     平均约 -0.14 s
/odom     平均约 -0.18～-0.27 s
```

负延迟不是机器人“提前发布”，而是 `ros2 topic delay` 把 PC 当前时间和 Jetson 消息的 header 时间戳直接相减，跨机器时会受到两台机器系统时钟偏差影响。PC 和 Jetson 虽都显示 NTP 已同步，但仍不能把这组数字当成真实网络延迟。

另外，自定义诊断程序如果使用默认 QoS 订阅 `/scan` 或 `/imu/data`，会出现：

```text
offering incompatible QoS
```

雷达和 IMU 使用传感器的 `BEST_EFFORT` QoS，诊断程序必须使用 `SensorDataQoS` 或 `BEST_EFFORT`，否则会误以为没有数据。

### 6.4 `/scan` 约 0.1 秒是否错误

当前雷达驱动在完整一圈扫描结束时发布上一圈数据：

```cpp
pre_time_ = time_;
time_ = get_clock()->now();
scan.header.stamp = pre_time_;
scan.scan_time = time_ - pre_time_;
```

因此 `/scan` 的消息时间戳代表这一圈扫描的起始边界，消息在一圈结束后发布，约有一帧 `0.1 s` 的正常扫描周期差。这不是 `1.8 s` 的根因，但必须保证不能继续排队超过一圈。

## 7. 与参考工程的关键区别

### 7.1 与 `example/ros2-stm32-autonomous-robot` 的区别

该工程是最接近当前两轮差速车的参考：

- MCU 使用硬件正交编码器模式，当前底盘使用 CH3 双边沿捕获加 B 相判向。
- 参考固件发送左右轮独立累计计数、MCU 单调时间戳、序号和有效标志。
- 当前 `0xCD` 协议也已经携带序号、MCU tick 和左右累计计数，方向上已经接近参考。
- 参考桥接是 C++，当前桥接是 Python。参考 C++ 节点更不容易受到 Python 串口解析和 ROS 单线程回调阻塞影响。
- 参考桥接根据 MCU 时间戳计算 `dt`，当前桥接同样根据 `mcu_tick` 计算轮增量时间。
- 参考工程使用 `use_pose_extrapolator = true`，当前已经改回 true。
- 两者都使用 `tracking_frame = base_link`、`provide_odom_frame = false`、`use_odometry = true`、`use_imu_data = false`。
- 参考导航启动前等待 `map -> base_link` 新鲜，当前也增加了 `wait_for_localization.py`。
- 参考项目有更明确的底盘状态、通信超时和安全门，当前项目只有 `/cmd_vel` 超时停车，安全状态信息较少。

### 7.2 与 `example/ROS_SLAM` 的区别

`example/ROS_SLAM` 是四轮麦克纳姆底盘，不应直接复制：

- 它的 `tracking_frame` 使用 `imu_link`。
- 它开启了 `use_imu_data = true`。
- 它在 ROS 端用四轮速度积分，并且包含针对实车的平移比例补偿。
- 它转动时使用 IMU 角速度积分覆盖 yaw。
- 它没有当前 `0xCD` 这种带 MCU 时间戳、序号和累计计数的完整遥测方案。

它可以参考“转弯时 IMU 辅助”的思想，但不能把它的四轮运动学、IMU 轴和补偿系数搬到当前两轮差速车。

### 7.3 当前导航逻辑与参考工程的区别

当前导航仍比参考工程复杂：

- 当前保留了自定义 `ImuSpin` 行为插件。
- 当前 `DWB` 仍启用 `RotateToGoal`、`GoalAlign` 和 `PathAlign`。
- 当前 BT 已删除默认终点 IMU 旋转，但 DWB 仍可能为了路径方向输出原地转向。
- 参考安全 BT 只跟随路径，恢复行为使用 `Wait`，没有默认 `Spin`。
- 当前 `behavior_server` 同时注册了 `spin`、`backup`、`drive`、`wait`，后续要重点确认是否真的需要这些恢复行为。

如果再次出现“导航自己转圈”，优先检查：

```bash
ros2 topic echo /cmd_vel_nav --once
ros2 topic echo /cmd_vel --once
ros2 action info /navigate_to_pose
grep -E "spin|Rotate|Goal|Transform|progress|failed" /tmp/*.log
```

如果 `/cmd_vel_nav` 本身持续输出较大的 `angular.z`，问题在 DWB/BT/目标姿态；如果 `/cmd_vel_nav` 为零但 `/cmd_vel` 仍转，问题在 velocity smoother、IMU 行为插件或其他节点抢占 `/cmd_vel`。

## 9. 时间戳链路审计结论

### `/scan`

- 当前驱动以完整扫描起点 `pre_time_` 作为 `header.stamp`。
- `scan_time` 是相邻完整扫描边界的差值。
- 正常 10 Hz 时，消息年龄约一帧，即约 `0.1 s`。
- 如果年龄大于 `0.3～0.5 s`，应检查驱动发布线程是否被阻塞、数据处理是否堆积或网络/串口输入是否断续。

### `/odom`

- 当前桥接用 MCU tick 计算轮增量 `dt`。
- 发布消息和 TF 使用接收时的同一个 ROS `now`，因此 `/odom` 和 `odom -> base_link` 时间戳一致。
- 当前 Jetson 实测年龄约 `1～3 ms`，不是 1.8 秒根因。
- 未来如果底盘固件能提供可靠的 MCU 采样年龄，可以像参考工程的 IMU 一样把测量年龄折回 ROS 时间，但必须保证 PC/Jetson时钟和 ROS 时间一致，不能直接把 MCU tick 当 ROS 时间戳。

### `/imu/data`

- 当前 IMU 桥接在解析到四元数帧后使用 ROS `now` 发布。
- 当前 Jetson 实测年龄约 `1～4 ms`。
- `chassis_bridge` 的 IMU 回调使用 ROS 接收时间计算连续 yaw，当前 `imu_force_gyro_yaw = true` 时主要使用 `angular_velocity.z` 积分。
- 如果要进一步改进，必须先明确飞控四元数、gyro 轴、符号和消息时间戳，不能同时让 Cartographer 和底盘桥接各自独立积分同一个 yaw。

### TF

- `odom -> base_link` 由底盘桥接随 odom 更新。
- `map -> odom` 由 Cartographer 发布。
- `map -> base_link` 的年龄由两者中较旧的链路决定。
- Nav2 启动前使用 `wait_for_localization.py` 检查 `map -> base_link` 年龄不超过 `0.7 s`。
- 这只能阻止“启动时 TF 已经过期”，不能阻止运行中出现新的 1.8 秒卡顿，因此仍需要运行时监控和超时停车逻辑。

## 10. 后续改代码的建议顺序

### A. 先不要继续改 Cartographer 匹配参数

当前日志显示 Cartographer 的扫描和里程计输入频率正常，`constraint_builder` 分数也有正常值。继续调整 `rotation_weight`、扫描窗口或 `submaps.num_range_data` 可能掩盖真正的时间戳/底盘问题。

### B. 先把“偶发 1.8 秒”变成可复现证据

需要记录：

- `/scan` header 时间戳与 Jetson 当前时间的最大年龄。
- `/odom` header 时间戳与 Jetson 当前时间的最大年龄。
- `/imu/data` header 时间戳与 Jetson当前时间的最大年龄。
- `map -> odom`、`odom -> base_link`、`map -> base_link` 的最大 TF 年龄。
- 发生延迟同时的 CPU、进程状态和 Cartographer 日志。
- 是否存在消息序号跳变、底盘 tick 跳变和串口校验失败。

### C. 优先降低桥接阻塞风险

如果复现确认是 Python 节点卡顿，建议：

1. 串口接收移到独立线程。
2. ROS 回调只读取“最新完整底盘帧”，不在回调里长时间解析字节流。
3. IMU 解析和发布使用独立线程或 C++ 节点。
4. 底盘遥测保留序号、MCU tick、累计左右计数和有效标志。
5. 所有串口和 ROS 发布都增加丢帧、校验失败、队列积压统计。

### D. 再处理导航转圈

按以下顺序处理：

1. 确认导航目标箭头方向是否故意要求转弯。
2. 检查 `/cmd_vel_nav` 是否输出角速度。
3. 检查 `/cmd_vel` 是否被多个发布者同时发布。
4. 确认安全 BT 没有 `Spin` 或默认恢复行为触发。
5. 若只想先验证位置导航，可暂时把 `DWB` 的 `RotateToGoal` 从 critics 中移除，并把 `min_speed_theta` 设为 `0.0` 做诊断；不要直接作为最终参数提交。
6. IMU 终点方向控制单独通过 `/imu_spin` 验证后，再决定是否集成回 Nav2 行为树。

## 11. 当前不可误判的事项

- RViz 的 GLSL 报错 `active samplers with a different type...` 是 RViz/OpenGL 地图显示问题，不等于 Cartographer 算法错误；显卡驱动更新后仍需分开判断。
- RViz 的 `Message Filter dropping ... queue is full` 是 TF 不及时或消息年龄过大时的结果，不是根因本身。
- `Lookup would require extrapolation into the future` 表示查询时刻和 TF 缓存边界不一致，必须结合消息 header 时间、TF 年龄和节点时钟一起判断。
- `/scan` 正常的约 `0.1 s` 扫描起始时间差不等于网络延迟。
- PC 跨机测得的负 `ros2 topic delay` 不等于数据提前到达。
- 飞控 IMU 角度正确，不代表底盘左右轮计数、底盘 `odom` 平移和 TF 时间戳都正确。
- IMU 可以可靠修正 yaw，但不能单独提供二维平移位置；导航局部代价地图仍需要连续、及时的 `odom -> base_link`。

## 12. 交接验收标准

后续 AI 声称“可以导航”前，必须同时提供以下证据：

```text
1. 只有一个 Cartographer，没有 AMCL。
2. /scan 约 10 Hz，Jetson 端最大消息年龄小于 0.3 s。
3. /odom 约 50 Hz，Jetson 端最大消息年龄小于 0.1 s。
4. /imu/data 约 100 Hz，Jetson 端最大消息年龄小于 0.1 s。
5. map -> odom、odom -> base_link、map -> base_link 无持续过期。
6. 底盘静止时 /cmd_vel 为零，/odom 不持续漂移。
7. 直线低速行驶不明显偏航。
8. 原地左转和右转的 IMU yaw 与实车方向一致。
9. 导航短距离目标不会无故持续原地转圈。
10. 发生传感器或 TF 超时时，底盘能自动停车。
```
